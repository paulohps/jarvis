# Models, migrations, factories and seeders

## Friendly ids are the only public identifier
Exposed models use `App\Models\Concerns\HasFriendlyId` and declare `public static function idPrefix(): string` (unique, at most 5 chars, immutable: `usr`, `wsp`, `inv`, `shl`, `wtgt`…; grep `function idPrefix` before picking one). The migration adds `$table->friendlyId();` right after `$table->id();` (macro in `AppServiceProvider::configureSchemaMacros()`: `string(30)->unique()`). `getRouteKeyName()` becomes `friendly_id`; the numeric id never goes to a URL, API payload or the apps. Ids are generated by `App\Support\FriendlyId`.

## Internal pivots have no friendly id
`WorkspaceMembership` (`workspace_user`, an incrementing `Pivot`) and lookup rows have none. Admin Livewire screens address memberships by numeric id but always scope the query to the workspace (`WorkspaceDetail::membership()`); the API addresses a member by the user's friendly id.

## Lookup tables replace enums
Categorical values are rows of a lookup table (`id`, `name`, unique `slug`, extras like `is_active`), modelled by a subclass of `App\Models\Lookup` with slug constants (`Module::CHATS`, `InvoiceStatus::SENT`). Read them with `X::idFor($slug)` / `X::bySlug($slug)`, memoized per request/job by the scoped `App\Support\LookupCache`; an unknown slug throws `UnknownLookupSlug`. Never add a PHP enum or a string status column. A `Lookup` subclass that overrides `booted()` must call `parent::booted()` (it forgets the cache on save/delete).

## Lookup rows: seeder plus upsert migration
Rows live in `database/seeders/LookupSeeder.php::lookups()`, upserted by `slug` (idempotent; run by `jarvis:install`, which is safe to rerun). It writes through `DB::table()`, so it ends with `app(LookupCache::class)->flush()`. When a row must exist on already-migrated databases before the seeder runs again, also upsert it in a migration and flush the cache, as `2026_10_08_180000_add_web_device_platform.php` does. `notification_types` rows are not seeded here: `notifications:provision` creates them.

## New lookup tables
The base set is created in `0000_01_01_000000_create_lookup_tables.php` (runs before `users`). Later lookups (`chat_providers`, `ai_purposes`, `mail_service_types`) are created in their feature migrations; follow the same columns and add their rows to `LookupSeeder`.

## Workspace-scoped data
Shared data has a non-null `workspace_id` (`foreignId('workspace_id')->constrained()->restrictOnDelete()`) and the model uses `App\Models\Concerns\BelongsToWorkspace` with `workspaceModule()` returning its Module slug. There is no global scope: read with `->visibleTo($user)` and check with `$record->isVisibleTo($user)`. Add the table to `Workspace::SCOPED_TABLES` too, or `DeleteWorkspace` will delete a workspace that still has data. Example: `app/Models/ShoppingList.php`.

## Personal data stays per user
WhatsApp accounts, Slack accounts, chat conversations, mail services, Google calendars and devices belong to a `user_id`, outside any workspace. Do not add `workspace_id` to them.

## Morph map is enforced
`Relation::enforceMorphMap()` in `AppServiceProvider::configureMorphMap()` stores short aliases (`user`, `reminder`, `chat_scheduled_message`…). A new model used in a morph relation (e.g. `Schedulable` owner of `recurrences`, notifiable) must be added there and to the dataset in `tests/Feature/MorphMapTest.php`; otherwise it throws `ClassMorphViolationException`.

## Model declaration style
Use the attribute style already in place: `#[Fillable([...])]`, `#[Hidden([...])]` on the class, `protected function casts(): array`, accessors as `Attribute::get(...)`, scopes with `#[Scope]` or `scopeX`. Keep a class docblock describing the concept and `@property` / `@property-read` lines for every column and relation (PHPStan reads them). `is_super_admin`, `deactivated_at`, `email_verified_at` are not fillable: set them with `forceFill()`.

## Secrets are encrypted casts
Tokens, API keys and passwords of integrations use the `encrypted` cast (`SlackAccount::access_token`, `AiProviderConnection::api_key`, `GoogleCalendarAccount::refresh_token`, `MailService::secret`) and are listed in `#[Hidden]` when the model is serialized. Invitation tokens are stored only as a sha256 (`Invitation::hashToken()`).

## Soft deletes are selective
Only some models soft-delete (`User`, `ShoppingList`, `Reminder`, `InvoiceRecurrence`, `Issuer`, `Payer`, `WhatsappMessage`, `ShoppingListSchedule`, `AiProviderConnection`, `AiModelPrice`). Uniqueness checks on users include trashed rows (`User::withTrashed()`), and `Workspace::hasData()` counts soft-deleted rows.

## Status derived from timestamps
Prefer nullable timestamps over status columns when the state is a lifecycle: `Invitation` has `accepted_at`/`revoked_at`/`expires_at` and a computed `status` attribute; `User::isDeactivated()` reads `deactivated_at`.

## PostgreSQL only
Migrations may use Postgres features: partial unique indexes via `DB::statement('CREATE UNIQUE INDEX ... WHERE is_default')` (`workspace_user_single_default_unique`, `shopping_lists_single_default_unique`), `DISTINCT ON`. Tests run on pgsql too (`phpunit.xml`), so do not write SQLite fallbacks.

## Migrations
Anonymous classes, one concern per file, a docblock explaining why. Every migration has a working `down()`; data migrations move existing rows (see `2026_10_07_205932_create_workspaces_tables.php`, tested by `tests/Feature/WorkspacesMigrationTest.php`). Foreign keys to users that record who did something are `*_by_id` with `nullOnDelete()` (`created_by_id`, `added_by_id`, `enabled_by_id`, `invited_by_id`). `DB::prohibitDestructiveCommands()` is on in production.

## Module access tables
Module access is `module_workspace_user` (membership × module, with `enabled_by_id`), not `module_user`, which was dropped. `Module::users()` still points at the dropped `module_user` table: do not use it. Invitations keep their modules in `invitation_module`.

## Factories resolve lookups themselves
Tests run on an empty schema, so factories call `static::lookupId(Locale::class, Locale::EN, [...])` from `Database\Factories\Concerns\ResolvesLookups`, which creates only the missing row. Use it for every lookup FK in a new factory.

## Workspace-aware factories
`WorkspaceFactory::household()` is the default shared workspace. `UserFactory` states: `superAdmin()` (member of the household with every module implicitly), `withModules([...])` (household membership with those modules), `inWorkspace($workspace, [...], $color)`, `deactivated()`, `googleOnly()`, and the static `UserFactory::joinWorkspace()`. Factories of scoped models default `workspace_id` to the household.

## DatabaseSeeder stays minimal
`DatabaseSeeder` only runs `LookupSeeder` and `notifications:provision`; every seeder must be idempotent. Do not seed users or demo data: the super admin is created by `jarvis:install`.
